# Shipping a hello pc component

Anyone on the hello pc team can ship. There are **two separate destinations**, and
they move on different clocks:

Merging to `main` updates the docs. It does **not** ship the code — apps stay on
whatever version they installed until a new one is published. See
[Building a component](?path=/docs/hello-pc-maintenance-building-a-component--docs) for how to
author one in the first place.

## 1. Ship the component to Storybook

1. Branch, add `<Component>.tsx` + `<Component>.stories.tsx` + `index.ts`, and
   export it from `src/hellopc/index.ts` (the package's public barrel — a
   component missing from it cannot be imported by consumers).
2. Verify locally:

   ```bash
   npm run storybook          # eyeball it
   npm run build-storybook    # must exit 0
   ```

3. Open a PR. On merge to `main`, `.github/workflows/deploy.yml` rebuilds the
   site and Storybook goes live at `cake.lenovo.com/storybook`.

> The repo path contains an `&`, which breaks npm's generated `.bin` shims on
> Windows. The package scripts already invoke binaries through `node` for this
> reason — if you add a script, do the same.

## 2. Publish a package version

Publishing is what actually delivers the component to apps.

### Preferred: from the Actions tab (no tokens)

**Actions → “Publish design system package” → Run workflow →** enter the version,
leave **dry run** checked the first time. The dry run builds the package and
prints the manifest and exact file list without publishing. Re-run with dry run
unchecked to publish for real.

It authenticates with the automatic `GITHUB_TOKEN`, so nobody needs a personal
access token.

A real run does five things:

1. builds `dist-package/` from source;
2. publishes to **GitHub Packages** (`@cake-admin/cakeand`);
3. creates a **GitHub Release** and tags it `v<version>`, attaching the tarball —
   this is what designers install from, and it needs no token at all;
4. verifies that zero-auth install actually works, on a runner with no `.npmrc`;
5. opens a PR pointing `starter/` at the new version and regenerating
   `starter/context/` to match.

The version is validated up front: it must be semver, must not already exist as a
tag, and must be greater than the newest one.

> **Release assets are immutable.** Never delete a tag and re-upload under it.
> Every consumer's lockfile records a checksum of those exact bytes, so replacing
> them turns `npm ci` into an unexplainable integrity failure for everyone who
> already installed. Publish a new version instead.

### Fallback: from your machine

```bash
npm run build:package -- --version 4.1.0
cd dist-package
npm publish
```

This path needs a token with `write:packages` in your `~/.npmrc`:

```ini
//npm.pkg.github.com/:_authToken=${GITHUB_TOKEN}
```

### Choosing a version

Standard semver, because apps pin what they install:

- **patch** (`4.1.0 → 4.1.1`) — a fix, no API change
- **minor** (`4.1.0 → 4.2.0`) — a new component or a new optional prop
- **major** (`4.1.0 → 5.0.0`) — a renamed/removed prop, or changed default

Consumers don't receive a new version automatically: they upgrade when they run
`npm update`. That's deliberate — one CSS tweak shouldn't reshape twelve
prototypes mid-flight.

## 3. Resync the AI knowledge base

Agents in [`cake-admin/ai-lab`](https://github.com/cake-admin/ai-lab) build UI
from a machine-readable index of this design system. Regenerate it after adding
or materially changing a component:

```bash
npm run build:knowledge -- --out ../ai-lab/knowledge/components
```

Each entry is derived from the `docs.description.component` prose in the story —
the same text on the component's docs page — so the index cannot drift from the
docs. The generator **fills gaps only** and never overwrites a hand-curated
entry. Never hand-edit a generated file: fix the story's docs and regenerate.

The markdown that designers' coding agents read comes from the *same* parse, via
`scripts/build-agent-context.mjs`, so the two descriptions of a component can
never disagree. You do not need to run that by hand: the deploy workflow
regenerates the copy served at `cake.lenovo.com/context/`, and the publish
workflow regenerates the copy inside `starter/`.

One thing does need a human: a new component **folder** fails the generator until
it is added to the `CATEGORIES` map in that script. That is deliberate — a
component missing from the index is one that agents will never use.

## Syncing tokens from Figma

Colors, spacing, radius and stroke come from the Figma library's variables. They
reach the repo as JSON in the root `& color hero`, `& theme.a`, `& win hct` and
`& spacing` folders, and every token build reads from there.

**From a manual export (works today):**

1. In Figma, open the library → **Local variables** → export each collection:
   `hellopc hero`, `hellopc` (light.a + dark.a), the Windows High Contrast
   collection (light.a), `win hct system` (all four themes) and the spacing
   collection.
2. Put every downloaded `.json` file in one folder. Leave the names as Figma
   gave them, including duplicates like `light.a (1).tokens.json`.
3. Run:

```bash
npm run import:figma-tokens -- "C:\path\to\that\folder"
```

The script identifies each file by its contents, copies it into the right
`& …` folder, rebuilds the tokens, and lists any CSS variables that were added
or removed. It refuses to change anything if a file is unrecognized or two files
claim the same slot. Add `--dry-run` to only preview where each file would go.
Collections missing from the folder keep their current repo copy.

**Automatically (needs Figma Enterprise API access):** the **Sync tokens from
Figma** workflow runs on demand from the Actions tab. Its weekly Monday schedule
is commented out in `.github/workflows/figma-tokens.yml` until the setup below
is done; turn it on after the first manual run succeeds. It pulls the variables through Figma's
Variables API, rebuilds the tokens, and opens or updates a pull request on
`figma-tokens/sync` listing the added and removed CSS variables. Review it in
local Storybook in all three themes, then merge it like any other change.

**From your machine:**

```bash
FIGMA_TOKEN=<your token> FIGMA_FILE_KEY=<file key> npm run sync:figma-tokens
```

`npm run check:figma-tokens` (same variables) only reports whether the repo is
out of date. `node scripts/sync-figma-tokens.mjs --list` prints every collection
in the file. Use it when a sync fails because a collection was renamed, then
update the `OUTPUTS` map at the top of the script.

**One-time setup:**

1. The Variables API needs a **Figma Enterprise** seat. Create a personal access
   token (Figma → Settings → Security) with the `file_variables:read` scope.
2. In the GitHub repo, add the secret `FIGMA_TOKEN` and the variable
   `FIGMA_FILE_KEY` (the key in `figma.com/design/<KEY>/…`).
3. Either add a fine-grained GitHub token as the secret `FIGMA_SYNC_PR_TOKEN`
   (contents and pull requests: write), or turn on *Settings → Actions →
   Allow GitHub Actions to create and approve pull requests*. Without the
   token, GitHub won't run the **Verify Storybook** check on the sync PR.

## What "done" looks like

- [ ] Component, stories, and `index.ts` added, and exported from `src/hellopc/index.ts`
- [ ] New folders added to `CATEGORIES` in `scripts/build-agent-context.mjs`
- [ ] `npm run build-storybook` exits 0
- [ ] Merged to `main` → live in Storybook
- [ ] Version published (dry run first) → Release, tag, and starter PR
- [ ] Starter bump PR merged
- [ ] Knowledge base resynced and PR'd to `ai-lab`
